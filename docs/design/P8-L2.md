## 1. Heuristics checklist (admin-and-student web app)

**Source keys:**
- **N1-N10:** Nielsen's 10 heuristics (nngroup.com/articles/ten-usability-heuristics, opened).
- **W:** WCAG 2.2 AA (w3.org/WAI/standards-guidelines/wcag/new-in-22, opened).
- **RUI:** Refactoring UI (refactoringui.com, opened).
- **TS:** taste-skill §4/§9.
- **RD:** redesign-skill audit.
- **MIN:** minimalist-skill.
- **P:** Primer.
- **S:** Stripe Apps docs.

**Rows tagged DIR** conflict with the owner's agreed direction. P8-L3 reports them as direction questions, not as findings.

| # | Check | Source |
|---|---|---|
| H1 | Every async action shows its status near where it happened, and saves are announced (live region) | N1, P saving |
| H2 | Words match the domain (section, term, enrollment), not internal codes, and error copy names the field and the fix | N2, N9 |
| H3 | Every dialog, filter and import can be cancelled. A destructive action has a confirm step, with the focus starting on Cancel | N3, P confirmation dialog |
| H4 | The same control looks and behaves the same on every page; no one-off recipe | N4, Spec 3 §5.9 |
| H5 | Errors are prevented before submit: inline validation, preview before an import commits, disabled-with-reason rather than silent failure | N5, RD "no form validation" |
| H6 | Options are visible (filters as visible controls, the current term shown) rather than remembered | N6 |
| H7 | Power paths exist: a search shortcut, keyboard movement in grids, and URL-encoded filters a user can bookmark | N7, Stripe search "bookmark searches", Linear Cmd+K |
| H8 | No irrelevant data on screen; secondary data is de-emphasised by weight and colour, not removed | N8, RUI "de-emphasize to emphasize" |
| H9 | Hierarchy comes from weight and contrast before size; there are not many sizes | RUI "size isn't everything", TS 9.B |
| H10 | Text at 4.5:1, borders and focus at 3:1, in both modes | W 1.4.3/1.4.11, Spec 3 §7 |
| H11 | A focused element is never fully hidden behind a sticky header or footer | W 2.4.11 (new in 2.2) |
| H12 | Pointer targets are at least 24x24 CSS px (44 px on touch per Spec 3 §7) | W 2.5.8 (new) |
| H13 | Sign-in needs no cognitive test, and paste is allowed in the email field (magic link complies) | W 3.3.8 (new) |
| H14 | Nothing the user already typed is asked for again in the same flow (for example, the invite email reused on the accept page) | W 3.3.7 (new) |
| H15 | Help or contact appears in the same place on every page if it exists at all | W 3.2.6 (new) |
| H16 | Label above the input, error below it, no placeholder-as-label | TS 4.6 |
| H17 | A loading state is a skeleton shaped like the result, not shown for waits under 1 s | TS 4.5, P loading |
| H18 | An empty state says what is missing and offers the one action that fixes it. A filtered-empty view says "no match" and offers Clear filters, never "create first" | P empty states, S empty state, Spec 3 §5.4 |
| H19 | Status is not by colour alone: badges, clash notes and cell states carry text | W 1.4.1, Spec 3 §7 |
| H20 | Current location is marked in the global nav and in tabs (`aria-current`) | RD "no indication of current page", P underline nav |
| H21 | Numbers in tables are right-aligned. TS/RD also ask for tabular figures, which conflicts with D56: **DIR** (DM Sans has none) | P data table, RD typography |
| H22 | No em dash in UI copy, no exclamation marks in success messages, no "Oops" | TS 9.G, RD content |
| H23 | Icons: TS/RD/MIN call Lucide the "default AI" set and prefer Phosphor/Radix. **DIR** (Lucide is Spec 3 §3.3) | RD iconography, TS 9.E, MIN §2 |

| H25 | Accent: TS "Lila rule" discourages purple by default but allows it when the brand asks. **DIR**, which the owner has already answered (D57). Check only that the purple stays on actions, links and the current location | TS 4.2 |

**Other DIR items** (taste rules that clash with Spec 3; report, do not score):
- **Cards:** RD "generic card look (border + shadow + white)" and TS 4.4 "cards only when elevation communicates hierarchy". Spec 3 cards are bordered with a hover shadow.
- **Card grid:** TS 9.C "no 3-column equal cards" is aimed at marketing feature rows. Our 3-column card grid is a data grid, so read the rule as a question, not a finding.
- **Radius:** RD "vary the radius" and TS 4.4 "pick one radius scale". Spec 3 uses 4 px everywhere, which satisfies the TS lock and contradicts RD.
- **Press motion:** RD/TS press feedback `scale(0.98)` and 200-300 ms transitions. Spec 3 §3.5 allows colour and opacity at 150 ms only.
- **Theme switch:** RD "light/dark toggle always sun/moon". Check what our switch looks like.
- **Avatars:** RD "avatar circles exclusively". Spec 3 allows full round on avatars only.
- **Not applicable:** RD and MIN marketing rules (noise, grain, background imagery, picsum photos, hero rules, bento grids, scroll animations, logo walls). They do not apply to an admin and student app. P8-L3 should skip them, not report them.

### (b) App shell: top bar, navigation, search, theme switch, user menu

**Dribbble:**
- https://dribbble.com/shots/13384949-School-App-Dashboard-Mobile-Navigation (Ravi Joon). Two phones: a purple header with the student's name and class, a notice-board card row and a homework checklist; the menu is a full-screen purple overlay of 11 round illustrated icons with labels and a red "Logout". Worth noting: when a student has many destinations, a full-screen grid menu holds them on a phone. Would not survive: the illustrated icon set (we use Lucide) and the cartoon characters.

**Live products:**
- **Linear**, https://linear.app/enablement/guide/navigating-linear (opened).
  - The sidebar holds global nav: Inbox, My Issues, favourites.
  - Cmd/Ctrl+K opens a command menu that "runs any action or jumps to any page".
  - `/` opens a search across issues, projects and documents, and also accepts an id.
  - `G` then a letter jumps to a destination, and `?` lists all shortcuts.
  - Pattern: search is global, has a shortcut, and accepts both free text and an identifier.
- **Stripe Dashboard**:
  - Basics page, https://docs.stripe.com/dashboard/basics (opened). The sidebar is grouped into primary navigation, Shortcuts (pinned and recently visited) and Products, with settings split into Personal, Account and Product. `?` shows shortcuts.
  - Search page, https://docs.stripe.com/dashboard/search (opened). Top results appear as you type, and Enter goes to "View all results", grouped by object type, each group with "View all". Filters use `field:value` syntax. **"Search terms are included in the URL"**, so a search can be bookmarked.
- **Notion**, https://www.notion.com/help/keyboard-shortcuts (opened). Cmd/Ctrl+P or Cmd/Ctrl+K opens search or jumps to a recent page, and Cmd/Ctrl+[ and ] go back and forward.
- **GitHub**, theme settings at https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-personal-account-settings/managing-your-theme-settings (opened). Theme is a setting under Profile menu > Settings > Appearance, with "single theme" or "sync with system" (a day/night pair), plus dimmed, high-contrast and colour-blind variants. It is also reachable from the command palette. Pattern: the theme lives in the user menu or settings, not as a header toggle.
- **Primer navigation**, https://primer.style/ui-patterns/navigation (opened).
  - "Minimize the number of navigational elements".
  - The active item is marked.
  - Detail pages carry a back link or breadcrumbs.
  - On narrow viewports the sidebars hide, and filters move into a menu or a bottom sheet.

## 3. Cross-cutting patterns worth adopting

1. **Current location.**
   - Global nav marks the current item, and tabs carry `aria-current="page"`. Tab labels carry counts that load together, not one by one.
   - Detail pages have a back link to their parent.
   - Sources: Primer navigation and UnderlineNav, Linear sidebar, RD audit.
2. **Global search.**
   - One field with a keyboard shortcut (`/` or Cmd/Ctrl+K) shows top results as you type, and Enter goes to a full results page.
   - The query and filters live in the URL, so they can be bookmarked and shared.
   - It accepts an identifier (for us, a course code).
   - Sources: Stripe search, Linear, Notion. Ours already submits `q` to the Catalog (D59).
3. **Table density.**
   - Three densities exist (Primer). Spec 3 picks one at 48 px rows, which matches Primer "normal" in spirit.
   - Numbers are right-aligned, with one sort by default.
   - Row actions: at most one inline, the rest in a menu. Seen both ways: Untitled UI puts trash and pencil inline on every row, its Sergushkin rebound folds them into one kebab menu.
   - A title, a count and actions sit above the table ("Team members 48 users", Download CSV, Add user); position shows as "1-8 of 32".
   - Empty cells show a dash, not a blank (Mercury).
   - Sources: Primer DataTable, Untitled UI and Sergushkin team tables, Mercury activity log (seen).
4. **Course card anatomy.**
   - A colour band with the code doubles as identity, reused in the schedule (Canvas card colour, also used in its calendar).
   - Bold title, then one muted meta line (instructor, meetings).
   - A text badge (role or status), with actions or counts at the bottom aligned across the row (RD "buttons not bottom-aligned"). The Udemy-team card concept does this with a hairline divider above a footer row and a title clamped to two lines.
   - Per-course colour carried into the calendar is seen in two dashboard shots (Dissanayake, Szabaciuk), and both need five to eight pastel hues; that is the cost behind open question 7.
   - Sources: Canvas, Coursera result card, Udemy (D57), Hamza ERBAY card concept (seen).
5. **Form rhythm.**
   - Label above, helper text, error below. No placeholder-as-label.
   - One explicit Save per form; do not mix autosave with explicit save on one page.
   - Do not disable Save; validate on submit and say why.
   - Sources: TS 4.6, Primer saving.
6. **Destructive confirmation.**
   - The title is a question, the body states the consequence and lists the affected items, and the button is a verb ("Remove 3 members").
   - Initial focus is on Cancel.
   - One destructive style app-wide, red reserved for the destructive button, Cancel first (Hubacek modal, seen).
   - The Fastly modal, cited from its snippet in the first pass, turned out to be a counter-example: brand-colour confirm button with the initial focus on it.
   - Sources: Primer ConfirmationDialog, GitHub bulk remove review, Hubacek delete modal (seen).
7. **Skeletons.**
   - Shaped like the result: rows for tables, card blocks for grids. In a table skeleton the toolbar and column headers are real text and only the cells are bars, each sized to its column (Gopinathan, seen).
   - The shell, tabs and toolbar render first; only the content region waits (Mavenlink still, seen).
   - Never for waits under 1 s.
   - Announce the result count once (`role="status"`), not every skeleton.
   - Sources: Primer loading, Gopinathan and Mavenlink shots (seen).
8. **Empty states.**
   - The title says what is missing, and the action echoes the title.
   - A filtered-empty view says "no match" plus Clear filters, with no create call to action.
   - Section-level empty states are compact.
   - A table's column headers stay visible over its empty body (Hashemi, seen; the same shot offers "Search Again" instead of Clear filters, the counter-example to the line above).
   - Loading, error and empty states are kept distinct.
   - Sources: Stripe, Primer, Vercel Geist, Hashemi (seen).
9. **Toasts versus inline status.**
   - Primer avoids toasts for accessibility reasons and uses inline messages near the action, or a banner after a redirect. This agrees with D23 (no toasts).
   - TS 4.5 allows toasts "only for transient" messages.
   - Recommendation: keep inline status.
10. **Keyboard and focus.**
    - A shortcut list on `?`, and a search shortcut.
    - In grids, arrow keys or Tab between cells with Enter to edit (Google Classroom mentions grid shortcuts).
    - Focus never hidden under the sticky header (WCAG 2.4.11).
    - Sources: Linear, Stripe, Google Classroom, W3C.
11. **Responsive collapse.**
    - Tables become stacked cards at phone width when a row has 3-5 fields: key value top left, status badge top right, label-value rows, the main action full width at the foot, and column sorting replaced by one "Sort by" control (Shyaula and Honeycutt, seen).
    - Wide numeric grids (gradebook) keep the table with horizontal scroll, a frozen first column and a pinned total row (Vass, seen; Canvas freezes student names, product knowledge, not verified).
    - Tabs overflow into "More".
    - Filters go into a bottom sheet.
    - The week grid falls back to an agenda list under a day or week strip, items grouped by date with start and end time stacked (Michalczyk, Polkovnikov, Nikitin, Tsang, Shough, all seen).
    - Sources: Primer, Canvas Calendar, the shots named above.
12. **Draft, publish, finalize as visible states.**
    - A grade is visibly draft until returned or published, and the student-facing total explains when it is hidden.
    - Sources: Google Classroom draft and Return, Canvas posting, Classroom's shared overall grade.

## 4. Scoring rubric

Each criterion is scored 1-5. Each row describes what a 5 looks like. A 1 means the criterion is absent or broken, and a 3 means it is present but inconsistent. Score in both themes and at both widths; take the lower score.

**(a) Sign-in and magic link**
1. One column and one primary path: the email field and button come first, providers follow, full width with an icon and text.
2. The "link sent" state shows the address, resend and "use a different email".
3. Errors are inline under the field, in plain words, and the field keeps its value.
4. The wordmark and the form are the only things on the canvas; no marketing.
5. Paste works, autocomplete is `email`, and the target is 48 px.
6. Contrast passes in both themes, including the provider button borders at 3:1.

**(b) Shell**
1. The current page is unmistakable (weight plus underline plus `aria-current`).
2. Search is reachable by keyboard (`/`) and carries the query into the URL.
3. The header is at most 72 px and never wraps at 1024 px (TS 4.7).
4. The user menu, theme and university switch are grouped and labelled. Icon-only controls have a name and a title.
5. The skip link works, and focus is never hidden under the sticky header.
6. The phone layout keeps search and nav reachable without horizontal scroll.

**(c) My sections cards**
1. The card anatomy is fixed: band with code, bold title, one muted meta line, text badge.
2. The bottoms of cards in a row align. Variable meta does not shift the badge or actions.
3. The whole card is one link target with a visible focus. The hover shadow is the only motion.
4. The term picker is visible and says which term is shown.
5. The empty state names the term and the reason, and offers the one fixing action, or none if the viewer cannot act.
6. The grid goes 3, then 2, then 1 column with no orphan gaps, and spacing follows the 4 px grid.

**(d) Schedule**
1. Days and hours are scannable, and the current day is marked.
2. Each block shows code, time and room without truncation at 1440 px.
3. A clash is shown by text, not colour alone.
4. Block colour or identity matches the card.
5. Phone: an agenda or day list, never a squeezed 7-column grid.
6. Keyboard and screen-reader users get the same information (region per weekday).

**(e) Catalog**
1. Filters are visible, labelled, on one row, and stored in the URL.
2. The result count is announced (`role="status"`).
3. Result cards match My sections' anatomy.
4. A filtered-empty view says "no match" and offers Clear filters, with no create call to action.
5. Load more keeps the scroll position and moves focus to the first new item.
6. Phone: filters collapse into a disclosure or sheet, and the cards stack.

**(f) Section detail**
1. A title band answers code, title, term and instructors before any tab.
2. Tabs have a current state and counts.
3. Each tab's table follows (g).
4. There is a back link to the list.
5. Edit actions sit next to what they edit, and only for roles that may act.
6. Phone: the tabs overflow cleanly and the tables collapse.

**(g) Admin tables**
1. Header row: a title, a count and a primary action in a fixed spot.
2. Columns are aligned, numbers right-aligned, rows 48 px, hover visible in both themes.
3. Row actions: at most one inline, the rest in a menu, each with an accessible name.
4. Bulk selection, if present, shows a count in the toolbar ("2 Selected") and offers select-all-across-pages.
5. Long lists page or load more with a visible position.
6. The audit log is newest first, the actor-action-target-time columns read as one sentence, the action is a word (not a colour alone), timestamps are muted, and a date-range filter sits above it.
7. Phone: rows become stacked cards or scroll with a frozen first column.

**(h) Forms and dialogs**
1. Header, body and footer rhythm is identical across every dialog, with Cancel first.
2. Label above, error below. No placeholder-as-label. Save is never silently disabled.
3. A destructive confirm names the object and the consequence, focus starts on Cancel, and the danger style is reserved for this.
4. The import preview shows per-row outcome badges with text (new, exists, error) and a summary count before commit.
5. Focus is trapped in the dialog and returns to the trigger on close; Escape closes it.
6. Phone: the dialog fits at 390 px and the footer buttons stay reachable.

**(i) Gradebook**
1. Student names are frozen and assessment headers show title, max and weight (the one gradebook shot seen shows date and type but neither max nor weight).
2. A cell has visible edit, saving, saved and error states, announced by a live region.
3. Out-of-range input is flagged inline before save, by outline plus text, not fill colour alone.
4. A weight total that is not 100 shows a warning with text.
5. Finalize states why it is disabled, previews letters, and confirms.
6. Keyboard: Tab or arrows between cells, Enter or blur saves.
7. Phone: horizontal scroll with the frozen name column; no layout breakage.

**(j) My grades**
1. Term GPA and cumulative GPA sit at the top, with credit totals and their meaning labelled.
2. Each section shows the final letter, or the running percent with a "running" label.
3. Assessments are expandable, with points/max and weight.
4. Unpublished or hidden grades say why rather than show blank.
5. Numbers are right-aligned; the letter has emphasis and the decimals are muted (as in the Mercury log, (g)).
6. Phone: cards stack and nothing truncates.

**(k) Empty, loading and error states**
1. Loading is a skeleton shaped like the result, with none for waits under 1 s.
2. Error copy is plain and offers retry; no codes, no "Oops".
3. Empty copy states what is missing and the action echoes it.
4. Filtered-empty is distinct from first-use empty.
5. Loading, error and empty are never shown at the same time.
6. Results and errors are announced once.

**(l) Dark mode**
1. Every text pair is at least 4.5:1, and borders and focus at least 3:1.
2. Elevation reads through surface steps.
3. Purple links are legible, with the lighter tint per Spec 3.
4. No pure black, and no section that stays light.
5. Status colours keep their meaning and contrast.
6. Images and badges adapt.

**(m) Phone width**
1. No horizontal page scroll; only wide grids scroll inside their own container.
2. Targets are at least 44 px.
3. Nav and search are reachable within one tap.
4. Tables collapse by rule: cards if a row has at most 5 fields, otherwise scroll with a frozen first column.
5. Dialogs and sheets fit the screen.
6. The type scale stays readable (13 px minimum).

## 5. Open questions for the orchestrator (owner decisions)

1. **Taste-rubric conflicts:** report them only, or reopen any? The candidates are Lucide versus Phosphor, 400/700-only weights versus adding 600, bordered-plus-hover-shadow cards, and 4 px everywhere versus varied radius. All are listed as DIR in §1 and are not scored.
2. **Tabular figures:** Spec 3 §5.5 demands "tabular numbers" in tables, but D56 accepts that DM Sans has none. In the gradebook and GPA views, proportional digits misalign columns. Options:
   - accept D56;
   - use a second family for numerals only (breaks D58 "DM Sans alone");
   - check whether the DM Sans variable build exposes `tnum` (D56 says it does not).
3. **Mobile navigation:** Spec 3 §10 defers the mobile drawer. Should P8-L3 score phone navigation against a drawer or bottom tabs (references in (m)), or only against "reachable, no horizontal scroll"?
4. **Global search scope:** should search stay a Catalog search (D59), or become app-wide with a shortcut (Stripe/Linear pattern: sections, members, terms by role)? The second would be a Phase 9 feature, not a restyle.
5. **Theme control:** keep the header switch, or move the theme into the user menu or settings with a "sync with system" option (GitHub pattern)? A high-contrast theme is deferred in Spec 3 §10.
6. **Gradebook draft and publish model:** Google Classroom saves grades as drafts until "Return". Ours publishes per assessment. Is a per-student release out of scope? This is for P8-L3 to note only if our screens confuse publish and finalize.
7. **Course cover band:** Canvas lets each user pick a card colour, reused in the calendar. Should our band colour be per course or per department and carried into the week grid, or stay one pale purple tint (Spec 3 §3.1)? This touches D57's "purple only on ..." rule.
8. **Dribbble visibility:** 56 preview images were seen (§0), and ten shots were judged not useful. Is one preview frame enough for Spec 5 to cite a shot, or should the owner open the multi-screen and animated ones first?
