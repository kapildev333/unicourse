# Spec 11: Quizzes and assignments

Status: decided by the orchestrator under D8 delegation in an unattended `/loop` run, owner to confirm (D137-D145) · Date: 2026-10-08 · Builds on Specs 1, 4 and 6; visual rules from Spec 3; the taste-skill rubric (D78) applies to the web design

## 1. Intent

A section's staff set work for students inside UniCourse instead of a separate quiz tool: **quizzes** made of multiple-choice and fill-in-the-blank questions that open at a start time, close at an end time and are submitted automatically at the end, graded automatically and then reviewed by staff; and **assignments** with a start date and a due date that students answer with text and files and staff grade by hand. Both carry a title and a description. Every quiz and assignment is a gradebook column (Spec 4), so running grades, finalization, GPA and My grades keep working unchanged.

**Owner's brief (2026-10-08).** "We need MCQ, fill in the blanks questions and then automated and manual review of test in each course and then submission. After that we need separate assignment with due dates and start dates; assignment and test both should have title, description. Specially for test it should start at start time and finish and auto submit answers. Use spec driven and test driven approach." The owner's "test" is the domain word **quiz** here (D137): a Go package, a route or an e2e file named `test` collides with the software tests the repository is full of.

**Success criterion.** An instructor creates a quiz "Week 3 check" on a section (description, 40% weight, opens now, closes in two minutes) with two multiple-choice questions and one fill-in-the-blank question. A student signs in, opens the Quizzes tab, starts the quiz, answers two questions and stops. When the quiz closes, the server submits the attempt without the student doing anything; the student's page shows "Submitted automatically". The automatic grading gives the two answered questions their points. A TA opens the review page, accepts the student's unmatched fill-in spelling by giving the question its points, writes feedback and releases the scores; the student sees the score, the feedback and the correct answers; the gradebook column shows the same score. The same instructor creates an assignment "Essay 1" (description, due in a week, 20 points); a student submits a text and a PDF before the due date and replaces the text once; the TA downloads the PDF (same bytes as uploaded), enters 17 points and feedback; the student sees them once released. A second university sees none of it. An automated end-to-end test asserts all of it.

## 2. Out of scope

Question banks and reuse across sections · random question or choice order · more than one attempt · per-attempt time limits inside the window (the window is the limit) · partial credit on multiple choice · essay or numeric questions, images in questions · late submissions and late penalties · rubrics, peer review, plagiarism checks · group assignments · rich text (plain text with line breaks, as Spec 6) · regrading every attempt when an answer key changes after attempts exist (§8) · notifications when a quiz opens or an assignment is due (§8) · proctoring, lockdown, IP restrictions · LTI or external tools.

## 3. Domain model

New tables are tenant-scoped with RLS, composite tenant FKs (D19), `created_at`/`updated_at` with the trigger (D20), `(university_id, id)` uniques where another table references them. Migration `0010_quizzes_and_assignments.sql` (`0008` and `0009` belong to Phase 17, D145). All timestamps are `timestamptz`; every time comparison runs in the database with `now()` (D30).

| Entity | Fields | Rules |
|---|---|---|
| `assessments` (existing, Spec 4) | + `kind text not null default 'manual'` (`manual`, `quiz`, `assignment`); + `description text not null default ''` (≤ 10,000); + `opens_at timestamptz`, `closes_at timestamptz` | `opens_at` and `closes_at` are both set when `kind` is `quiz` or `assignment` and both null for `manual` (check constraint); `opens_at < closes_at`. For a quiz `max_points` is the sum of its questions' points, maintained by the server on every question write (a quiz with no questions keeps `max_points` 1 and cannot be started). `due_on` (Spec 4) is set by the server to `closes_at` as a date in the university's timezone for both kinds, so the gradebook and My grades show it without change. `published` keeps Spec 4's meaning: scores, per-question results and answer keys are visible to students only when true (D138) |
| `questions` | `university_id`, `assessment_id` (a quiz), `kind text` (`choice`, `blank`), `prompt text`, `points numeric(7,2)`, `position integer`, `choices jsonb not null default '[]'`, `answers jsonb not null default '[]'` | `prompt` 1..2,000; `points` > 0 and ≤ 1,000; `choice`: `choices` is 2..10 objects `{ "text": ≤ 500 chars, "correct": bool }` with at least one correct; `blank`: `answers` is 1..20 accepted strings, each 1..200 characters; FK `(university_id, assessment_id)` on delete cascade; positions 1..n dense, renumbered by the server (Spec 6 pattern); ≤ 100 questions per quiz; validated by the handler, the database only stores (D139) |
| `attempts` | `university_id`, `assessment_id`, `user_id`, `started_at`, `submitted_at` nullable, `auto_submitted boolean default false`, `answers jsonb not null default '{}'`, `grading jsonb not null default '{}'`, `score numeric(7,2)` nullable, `feedback text not null default ''`, `reviewed_by uuid` nullable, `reviewed_at timestamptz` nullable | unique `(university_id, assessment_id, user_id)`: one attempt per student (D140); `answers` maps question id to `{ "choices": [index…] }` or `{ "text": "…" }` (≤ 100 entries, text ≤ 1,000); `grading` maps question id to `{ "points": "2.00", "correct": bool, "feedback": "…" }`, written at submission by the automatic grading and edited by review; `score` = Σ `grading[*].points`, written to `scores` (Spec 4) in the same transaction; FKs `(university_id, assessment_id)` on delete cascade, `user_id` on delete cascade; index `(assessment_id, submitted_at)` |
| `submissions` | `university_id`, `assessment_id` (an assignment), `user_id`, `body text not null default ''`, `submitted_at`, `score numeric(7,2)` nullable, `feedback text not null default ''`, `graded_by uuid` nullable, `graded_at timestamptz` nullable | unique `(university_id, assessment_id, user_id)`: one submission per student, replaceable until `closes_at` (D142); `body` ≤ 20,000; `submitted_at` is the last write by the student; a submission needs a body or at least one file; `score` ≤ `max_points` × 2 (bonus, as Spec 4 scores) |
| `submission_files` | `university_id`, `submission_id`, `file_name`, `content_type`, `size_bytes`, `sha256`, `position`, `uploaded_at` | the `materials` rules of Spec 6 §3 (allowlist §6, 100 MB, base name ≤ 255, content type from the extension); ≤ 10 files per submission; FK `(university_id, submission_id)` on delete cascade; blobs live at `UNICOURSE_FILES_DIR/<university_id>/<file_id>` next to the materials (ids are UUIDs, no clash); `unicourse-admin prune-files` learns the second table |

**Automatic grading** (pure function in `internal/quiz`, unit-tested first): a `choice` question earns its points when the set of chosen indexes equals the set of correct indexes, else 0; a `blank` question earns its points when the answer, trimmed, lower-cased and with runs of whitespace collapsed to one space, equals one of the accepted answers normalised the same way, else 0; an unanswered question earns 0 and is `correct: false`. Points are `numeric` strings handled with `math/big` like Spec 4 (never floats).

**Submission** (one function, called by the student's submit and by the sweeper): grades the answers, writes `grading` and `score`, sets `submitted_at` (`now()` for a student submit, `closes_at` for an automatic one) and `auto_submitted`, upserts the `scores` row for `(assessment_id, user_id)` with `graded_by` = the student, and writes the audit row `attempt.submit` (`after` carries `score`, `auto`). The sweeper (`quiz.Sweeper`, started in `cmd/api/main.go` like the outbox sender, polling every 10 seconds) lists universities in a platform transaction and, per university under `pg.WithTx`, submits every attempt whose quiz has `closes_at <= now()` and `submitted_at is null`; rows are claimed with `for update skip locked` so several API processes never grade one attempt twice. Students whose window closed without them ever starting get no attempt and no score (a missing score counts as 0 at finalization, Spec 4 §3).

**Review** (D141): staff replace `grading` entries (`points` 0..question points, `feedback` ≤ 2,000) and the attempt's `feedback` (≤ 5,000); `score` and the `scores` row are recomputed; `reviewed_by`/`reviewed_at` set; audit `attempt.review` (`before`/`after` carry the score). Review is allowed only on a submitted attempt (409 `conflict` otherwise).

**Assignment grading** (D141): staff set `score` (0..`max_points` × 2) and `feedback`; the `scores` row is upserted; audit `submission.grade`. Grading is allowed any time after a submission exists (also after `closes_at`; the gradebook's inline entry remains for students who never submitted).

**Audit.** `assessment.create/update/delete` already exist (Spec 4) and now carry `kind`, `description`, `opensAt`, `closesAt`. New: `question.update` (one row per `PUT`, `after` carries the question count and total points), `attempt.start`, `attempt.submit`, `attempt.review`, `submission.update` (student writes, one row per `PUT` and per file add or remove, `after` carries body length and file names), `submission.grade`.

## 4. Authorization

| Who | Can |
|---|---|
| instructor or TA of the section, admin, dept_admin of the department (= `authz.CanEditContent`, Spec 6; TA parity) | create, edit and delete quizzes and assignments; edit questions; list and read every attempt and submission; download submission files; review attempts; grade submissions; publish (release) through `Assessment.published` as Spec 4 (a TA may release because review is score entry, Spec 4 §4 and D74) |
| enrolled student | list the section's quizzes and assignments (every `quiz` and `assignment` row from creation, D138; `manual` rows only when published, Spec 4); read a quiz's questions only between `opens_at` and `closes_at` or after submitting; start an attempt, save answers and submit within the window; read own attempt; see `grading`, `score`, `feedback` and the answer keys only when the assessment is published; write own submission and files within the window; read own submission; see score and feedback only when published; download own files |
| any other active member | 403 on every route of this spec |

Checks run in this order, as every handler: section exists (404) → role predicate (403) → window and state (409) → body validation (400). RLS underneath bounds any mistake to the university.

## 5. API

Routes under `/api/v1/universities/{slug}`; conventions D16 (no `null`, optional = omitted, arrays always present); error envelope and pagination as Spec 1 §6; every route in `openapi.json` with a `Who:` line; `types.ts` regenerated; the Postman collection regenerated (D109).

**`Assessment` widened** (Spec 4 §5): `{ id, sectionId, kind, name, description, maxPoints, weight, dueOn?, opensAt?, closesAt?, published, position, questionCount? }` (`questionCount` on quizzes, staff and students alike). `POST /sections/{id}/assessments` takes `kind` (default `manual`), `description` (default `""`), `opensAt`, `closesAt` (RFC 3339; required for `quiz` and `assignment`, rejected for `manual`); `maxPoints` is rejected for `quiz` (`validation_failed` on `maxPoints`, "derived from the questions") and required for the other kinds. `PATCH` may change `description`, `opensAt`, `closesAt` (the same rules; a quiz with submitted attempts may still move `closesAt` later, which reopens nothing already submitted) but never `kind`. Students' `GET /sections/{id}/assessments` lists `quiz` and `assignment` rows whatever `published` says and `manual` rows only when published; `GET /me/grades` (Spec 4) unchanged in shape and lists the new kinds under its existing rule, so a student's grades page shows a quiz score only once released.

## 8. Deferred, with triggers

| Deferred | Add when |
|---|---|
| Regrading when a key changes after attempts exist | the first instructor who must fix a key for a large section; `grading` is recomputable from `answers`, so it is a loop over submitted attempts that keeps reviewed entries |
| Several attempts, best or latest kept | the first course that runs practice quizzes; `attempts` gains an attempt number in the unique key |
| Per-attempt time limit inside the window | the first quiz where students may start at different times; `attempts.started_at` plus a `time_limit_minutes` column and the same sweeper |
| Late submissions with a penalty | the first instructor who asks; `closes_at` becomes the hard close and a `due_at` is added |
| Question banks and shuffling | the first department that shares quizzes across sections |
| Mail when a quiz opens or an assignment is due | students ask; the outbox exists |
| An "Upcoming" list across sections for a student | first student feedback; `GET /me/grades` already carries every assessment with `dueOn` |
| Essay questions graded by hand | the first instructor who asks; a third `kind` with no automatic points |

## 11. Scale and fit

A section of 300 students and a 50-question quiz is 300 attempt rows with a 50-entry `answers` map each; autosave is one `UPDATE` per student per change; the sweeper's pass is one indexed query per university every 10 seconds. The jsonb answers are the ceiling: when a department wants per-question statistics across sections, `answers` and `grading` move to an `answers` table (one migration, the grading function unchanged).
